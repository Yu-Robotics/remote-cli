# Scheduling host and event-adapter boundaries

Reviewed 2026-11-11 at remote-cli checkpoint `c1351b523745ba2ffd03ec5cb4e189084a8c1f78`.

## Decision

**Neither OpenCode 2.2.7 nor the reviewed ZCode distribution qualifies through the required existing transport and supported host/plugin seams.** This is a scoped integration verdict, not a claim that either product lacks native scheduling.

| Gate | OpenCode 2.2.7, ACP | ZCode 3.17.2 / bundled CLI 0.17.1, app-server |
| --- | --- | --- |
| Native scheduler exists | Yes; already starts behind ACP | Yes; owned by desktop composition |
| Model-tool management is a valid route | Yes; native schedule tools | Yes; native Cron tools issue reverse host RPCs |
| Supported configuration supplies required native host | Yes | No for the reviewed headless app-server/server entrypoints |
| Supported event-only adapter reaches existing protocol writer | No; server plugins cannot access ACP writer | App-server event subscription works, but does not supply the missing scheduler/dispatcher |
| Enable a remote-cli provider now | **No** | **No** |

The same rule admits DSH: its supported `--patch` loads the complete first-party scheduling dependency closure, and its plugin receives `ctx.acpTransport.notify(...)`. The existing [DSH report](agy-kimi-dsh-native-scheduling-verdict.md#dsh-supported-composition-and-authoritative-event-adapter) records native idle firing and correlated success/error extension notifications. Missing stock listeners alone are **not** a disqualification. The question here is whether a supported seam can connect the missing pieces without creating another automation host or modifying the backend.

## OpenCode: supported plugin RPC does not bridge ACP

The native clock is not the blocker. [`server/process.ts:118`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/server/src/process.ts#L118) starts scheduling in standalone servers, and [`handlers/acp.ts:24–35`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/cli/src/commands/handlers/acp.ts#L24) starts that server before constructing ACP.

The candidate event-only plugin route was traced through its actual implementation:

1. **Event subscription and emission are supported.** Public [`Plugin.Context:27–60`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/plugin/src/promise/plugin.ts#L27) exposes `event`, `session`, and `rpc`. [`RpcDomain:19–31`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/plugin/src/promise/rpc.ts#L19) lets a plugin register methods and emit events. However, [`core/rpc.ts:87–103`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/core/src/rpc.ts#L87) publishes those events to the **native server bus**. This is not an ACP notification API.
2. **The ACP writer is in another process and is not a plugin host export.** [`standalone.ts:17–46`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/cli/src/services/standalone.ts#L17) spawns `serve --stdio --port 0`. The parent reads its first readiness line and continues draining child stdout; it does not forward those lines to ACP. Writing ACP-shaped JSON from a server plugin therefore does not reach the client. Plugin entrypoint resolution is explicitly `server`, `tui`, `rpc`, and `gui`, with no ACP entrypoint ([`plugin/host.ts:13–23,56–63`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/plugin/src/host.ts#L13)).
3. **An internal extension writer exists, but is not exposed to plugins.** [`acp/connection.ts:32–58`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/cli/src/acp/connection.ts#L32) owns `extNotification`. [`acp/agent.ts:120–137`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/cli/src/acp/agent.ts#L120) registers the fixed `_session/steering` extension and passes the connection to internal ACP services. It does not register plugin RPC handlers or expose the connection in the public plugin context. Both Promise and Effect contexts have the same boundary; `ctx.app` is only name/version/channel metadata.
4. **Publishing a plugin event cannot bypass the stock filters.** The persistent [`sessions.ts:53–59`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/cli/src/acp/sessions.ts#L53) listener accepts only model/agent selection changes. The other persistent listener only reloads catalogs ([`catalog.ts:67–78`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/cli/src/acp/catalog.ts#L67)). Output subscriptions close after a prompt without live children; retained subscriptions filter to tracked children ([`turn.ts:203–209,307–323`](https://github.com/anomalyco/opencode/blob/fedc6f208aa2bd54c1019227214568083f6380ad/packages/cli/src/acp/turn.ts#L203)).

**Blocking seam:** native server event bus → ACP connection. Unlike DSH, the supported plugin receives no ACP transport capability. Configuring a server plugin, enabling native schedules, or keeping one process per job does not change that boundary. An HTTP event consumer, custom IPC/ACP proxy, private CLI imports, or an upstream ACP code change would add the missing transport path; none is the requested supported plugin composition in this version.

The smallest upstream change would expose a scoped plugin notification bridge, or forward native scheduled-run events through an ACP extension. After such a seam exists, the concrete acceptance probe is an idle ACP session with native once/recurring jobs: verify job/run/session correlation, success/error terminal events, and deletion receipts without further prompt input. Repeating default idle probes now would not test a new supported route.

## ZCode: headless host services do not compose the scheduler

The prior real CLI probes already established native Cron execution, reverse `automation/*` requests, error receipts, and persistent `session/event` framing. Those facts remain valid. The gap is native hosting, not model-tool availability or a pending-turn listener.

**App-server configuration cannot replace the host dependency.** The complete strict CLI flag parser is [`arguments.ts:3–110`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/apps/zcode-cli/packages/cli/src/arguments.ts#L3). Its protocol launch branch passes streams, environment, surface and storage-preparation options to `runZCodeProtocolAgent` ([`run.ts:252–293`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/apps/zcode-cli/packages/cli/src/run.ts#L252)). Session construction installs `createProtocolAutomationPort` ([`server-operations.ts:3616`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/apps/zcode-cli/packages/bootstrap/src/zcode-protocol/server-operations.ts#L3616)); that port sends CRUD to the client. Surface selection, MCP configuration and storage preparation do not substitute an in-process scheduling host. The `__zcode-plugin-host` route loads an MCP server's `main()` in its own invocation ([`plugin-host-command.ts:23–63`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/apps/zcode-cli/packages/cli/src/plugin-host-command.ts#L23)); it is not the desktop scheduler/host composition API.

**The official headless server was checked separately.** `zcode serve`'s Core calls `createServerHostServices`, then starts HTTP/WS and process lifecycle tracking ([`server-core/core.ts:55–71`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/zcode-server-cli/src/server-core/core.ts#L55)). That factory selects `standalone-server` and constructs services without the desktop dispatch callback ([`services/node.ts:3275–3323`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/services/src/node.ts#L3275)). It supplies host management services, not the native clock and dispatch composition. The official packaging boundary explicitly excludes Electron, Desktop Main and Window Host ([architecture contract, line 278](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/docs/architecture/r2-server-cli-and-daemon.md#L278)). Its advertised `desktopContinuous` capability is a WS delivery mode, not a scheduler switch ([`http.ts:230–235,294–304`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/zcode-server-cli/src/server-core/http.ts#L230)). `proxy-stdio` merely pipes bytes to that daemon ([`proxyStdio.ts:39,84–86`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/zcode-server-cli/src/server-core/proxyStdio.ts#L39)); it does not translate it into app-server JSON-RPC.

**The native scheduler requires the desktop dispatch chain.** Desktop Main starts it only after local database readiness ([`main/index.ts:2219–2236`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/desktop/src/main/index.ts#L2219)). The scheduler's native timer emits `cron-dispatch-request` through `process.parentPort` ([`scheduler/index.ts:181–202,431–449`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/desktop/src/scheduler/index.ts#L181)). Main explicitly rejects dispatch with `no local host available` if no host exists ([`desktopCronScheduler.ts:120–130`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/desktop/src/main/desktopCronScheduler.ts#L120)). The host receives `CronRun` on its Electron parent port and rejects it until database startup is ready ([`host/index.ts:3062,3232–3264`](https://github.com/zai-org/ZCode/blob/a9fe401eede6e6e5e01be9048679c206fe6f02d9/packages/desktop/src/host/index.ts#L3232)). It then owns task creation/resume, prompt dispatch and outcome accounting. Running the scheduler bundle under plain Node leaves its optional parent-port send without a recipient; running the host bundle under plain Node does not provide its required parent port.

**Blocking seam:** there is no supported headless entrypoint in the reviewed composition that joins the first-party clock, repository, dispatch host and app-server ownership. Importing repositories or answering reverse CRUD is insufficient. Recreating Electron parent-port routing, host initialization and dispatch ownership in remote-cli would be a custom automation host, beyond the permitted event adapter. Keeping the complete desktop running would retain native scheduling but is a different hosting composition; it does not make the existing remote-cli-owned app-server its scheduler client.

Reconsider when an official headless scheduler/dispatch host exposes attachment to the existing app-server protocol. The next concrete probe would then verify real CRUD receipts, idle firing, native run-trace correlation and terminal outcomes in that documented composition. No missing listener alone blocks ZCode.
